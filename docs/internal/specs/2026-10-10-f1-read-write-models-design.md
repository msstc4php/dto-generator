# F1 — модели чтения и записи (`readOnly` / `writeOnly`)

**Дата:** 2026-10-10 (UTC). **Статус:** решение принято автономно по поручению владельца 2026-10-10 («поддержка
readOnly/writeOnly — для неё нужны отдельные модели запроса и ответа… потом это»). Пересмотр — по замечаниям
владельца.

## 1. Проблема

OpenAPI помечает свойство `readOnly: true` («только в ответах») или `writeOnly: true` («только в запросах»). Одна
PHP-модель на схему не может быть честной для обоих направлений: обязательное `id` с `readOnly` не придёт в запросе,
и конструктор DTO запроса его потребует; `password` с `writeOnly` не придёт в ответе. Сейчас генератор эти ключевые
слова игнорирует (`docs/openapi-support.md`).

## 2. Решение

Настройка `dto.readWriteModels`:

- `single` (по умолчанию) — как сейчас: одна модель, `readOnly`/`writeOnly` игнорируются. Обратная совместимость.
- `split` — для каждой схемы, модель которой зависит от направления, генерируются две модели: **представление
  чтения** (`<Name>Read`, ответ: без `writeOnly`) и **представление записи** (`<Name>Write`, запрос: без `readOnly`).
  Модели, не зависящие от направления, остаются одной общей моделью без суффикса.

Суффиксы — `dto.readWriteSuffixes: {read: Read, write: Write}`: непустые идентификаторы PHP, различные. Пример
`{read: Response, write: Request}`.

## 3. Направленность свойства

Свойство направлено, если `readOnly: true` или `writeOnly: true` стоит на схеме свойства или на любой схеме её цепочки
`$ref` (как `SchemaReferences::chain()`: `{$ref: AuditInfo}` со схемой `AuditInfo: {readOnly: true, …}` делает
свойство readOnly). Схема `additionalProperties` — тоже свойство (`$additionalProperties`).

- `readOnly` и `writeOnly` вместе — warning «… are both true; the property is in both views», свойство не направлено.
  Флаги свойства собираются со всех членов композиции (`allOf`), которые его объявляют: флаг у любого считается,
  `readOnly` у одного и `writeOnly` у другого — оба (ревью CR-001, CR-003). Одно правило — для анализа зависимости,
  фильтра свойств и выноса инлайн-классов.
- Значение не `true`/`false` — warning, игнорируется (как сейчас для любых неподдержанных значений).
- Направленность самой схемы класса (`Pet: {readOnly: true, properties: …}`) на её свойства не распространяется: она
  действует там, где на `Pet` ссылаются как на значение свойства.

## 4. Какие классы зависят от направления

Класс зависит от направления (замыкание до неподвижной точки), если:

1. у него есть собственное направленное свойство;
2. тип собственного свойства ссылается (через список, map, nullable, union) на зависимый класс;
3. зависим его родитель (наследник получает свойства родителя);
4. он — дискриминированная база, и зависим один из её вариантов (mapping должен указывать на представления), или
   зависима база одного из его вариантов — по п. 3.

Enum-ы не зависят никогда. Анализ идёт по пробной сборке в режиме `single`: собственная направленность — по
составу каждой объектной схемы, включая схемы, чьё имя занял другой класс (ревью CR-002); связи — по IR (типы
свойств, родитель, дискриминатор), обходом в ширину по обратным рёбрам. Без зависимых классов результатом остаётся
пробная сборка (плюс предупреждения о флагах) — две сборки не нужны.

## 5. Построение представлений

`Build` запускается для каждого направления с параметром «представление»:

- имя зависимого класса — его обычное имя (схема, `x-php-class-name` или `<Parent><Property>…` для инлайн-классов,
  выведенное от **базового** имени владельца) плюс суффикс: `PetRead`, `PetOwnerRead` (не `PetReadOwner`);
- `ClassBuilder` пропускает свойства противоположного направления, как `x-php-skip`; обязательное пропущенное свойство
  предупреждения не даёт;
- ссылки, наследование, дискриминаторы, инлайн-классы строятся штатным механизмом: `TypeMapper` и `ClassLookup` находят
  представление через объявления `Registry` по location.

Результаты двух сборок сливаются (`Build\Views`): зависимые классы — оба представления, общие — один раз, enum-ы —
один раз. Общий класс одной схемы, вышедший в двух сборках по-разному, — ошибка «defect of the generator» (страховка).
Диагностика сборки записи, которая после замены имён представлений записи на имена чтения совпадает с диагностикой
сборки чтения, отбрасывается: проблема зависимого класса сообщается один раз, с именем представления чтения.
Диагностики пробной сборки отбрасываются. `RequiredCycles` проверяется в каждой сборке. Инлайн-классы свойств другого
представления в сборке не объявляются.

Имя представления, занятое другим классом (схема `PetRead`), — ошибка «Class … is already generated from …» с
подсказкой `x-php-class-name` или `dto.readWriteSuffixes`.

## 6. Обогащение и мост

`Enrich` получает классы представлений как обычные классы: `ClassContext::schema()` — та же схема для обоих,
свойства — те же схемы. Мост Symfony работает без изменений: `DiscriminatorMap` строится из `DiscriminatorModel`
представления, ограничения валидатора — только для свойств представления. README моста упоминает режим.

## 7. Вне рамок

- Отдельная настройка на схему (`x-php-read-write`).
- Представление «как в single» в дополнение к двум (третья модель).
- Направленность значений внутри `items` без свойства (элемент списка `readOnly`) — игнорируется, как в `single`.

## 8. Совместимость

`single` по умолчанию — вывод не меняется. Включение `split` переименовывает зависимые классы (старые файлы удаляет
менеджер записи по манифесту) — это осознанный шаг пользователя, CHANGELOG описывает его в «Added».

## 9. Тестирование

- Юнит: направленность (цепочка `$ref`, оба флага, значения не bool), зависимость (ссылки, наследование, варианты,
  map/list/union), имена (инлайн, `x-php-class-name`, коллизия), фильтр свойств.
- Интеграция: `generate` в режиме `split` на схеме с `id` readOnly, `password` writeOnly, вложенным объектом,
  иерархией `allOf` и дискриминатором; эмиттер на 7.4/8.2; повторный прогон — `unchanged`.
- Мост: `RealSymfonyTest` — сериализация представления чтения, валидация представления записи.
- Infection: MSI 100 %.
